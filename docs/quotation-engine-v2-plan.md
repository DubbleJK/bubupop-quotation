# 견적 엔진 v2 설계

기준 커밋은 1차 안정화 `fe542d6`, 2차 계산 수정 `a43d9b6`이다. 이 문서는 설계만 다룬다. 기존 8개 품목의 판매가 계산, 관리자 판매 설정, 운영 KV는 바꾸지 않는다.

우선 기능은 관리자가 코드를 고치지 않고 원자재·제작 공정·판매 품목을 추가한 뒤, 원가를 입력하면 적정 판매가격, 공헌이익, 이익률을 계산해 보여주는 것이다. 추천가격은 계산 결과에 머물고, 관리자가 승인하기 전에는 고객 견적 판매가로 바뀌지 않는다.

이 문서는 구현 전에 확정할 최종 설계다. 설계 확인 전에는 계산 코드, 판매가, 운영 KV, 운영 배포를 진행하지 않는다. 배포 절차는 14절에 적고, 이번 작업에서는 실행하지 않는다.

판매가격과 원가는 다른 층이다. 코드에 있는 미터당 판매단가, 장당 판매단가, 티셔츠 판매단가를 매입원가로 복사하지 않는다. 원가, 목표 이익률, 이익금은 공개 `/api/config`와 브라우저의 일반 견적 데이터에 넣지 않는다. 조회와 시뮬레이션은 관리자 세션이 있는 서버 API에서만 한다.

값의 상태는 세 가지다.

| 상태 | 의미 |
| --- | --- |
| 확인됨 | 매입 증빙이나 작업자 확인으로 원가·공임이 정해진 값. 현재 코드에는 이 상태의 매입원가가 없다. |
| 코드 참고값 | 지금 계산이나 화면 표시에 쓰이는 숫자. 판매 정책이거나, 원가처럼 보이지만 매입 증빙이 없는 값. |
| 미확인 | 설계에 칸은 있으나 숫자가 없는 값. 견적 판매가로 사용하지 않는다. |

## 1. 현재 코드에서 재사용할 부분

### 1.1 지금 판매가 산정

부가세 0.1과 10원 반올림(`roundToNearest10`, `calcVatAndTotal`)은 POP, 스티커 시트, 솔벤트, DTF, 티셔츠, 명함, 배너가 공유한다. UV키링은 1원 반올림과 코드 안 부가세 0.1을 따로 쓴다. 화면의 대표 금액은 공급가이고, UV만 부가세와 조정이 포함된 최종가다.

| 품목 | 판매가 | 코드 기본 판매 설정 |
| --- | --- | --- |
| POP | 배치 길이(m) × 4-cut 또는 2-cut 미터 단가. 양쪽이 롤 폭을 넘으면 견적 불가. | 4-cut 63,452원/m, 2-cut 55,046원/m, 롤 610mm |
| 스티커 시트 | 작업비 + 필요 매수 × 재질·용지 장당 단가. 최소 공급가 적용. 배치 불가면 그 용지는 견적 불가. | 작업비 15,000원, 최소 20,000원. 아트·모조 A4 500원, A3 980원. 유포 A4 950원, A3 2,100원. 투명데드롱 A4 950원, A3 불가 |
| 솔벤트 | 작업비 + 배치 길이 × 솔벤트 미터 단가. 양쪽이 롤을 넘으면 견적 불가. | 작업비 15,000원, 63,452원/m, 롤 620mm |
| DTF | 배치 길이 × 판매 미터 단가. 배치 불가면 견적 불가. 디자인 중 하나라도 불가면 합산하지 않음. | 판매 13,900원/m, 롤 850mm, 간격 7mm |
| UV키링 | 면적과 수량 구간 단가 × 수량, 부가세, 수량별 조정률. 관리자 설정 밖. | `uvAcrylicKeyring.ts` 상수 |
| 티셔츠 | (판매단가 × 수량 + 2XL 추가) × (1 − 주문 전체 할인율) | 반팔 18,000, 긴팔 20,000, 후드 25,000, 윈드브레이커 35,000. 2XL 3,000원. 10장 10%, 50장 20%, 100장 25% |
| 명함 | 등록 매수의 인쇄비 + 등록 등급의 디자인비 | 수입 당일제 100매 20,000 / 200매 25,000. 아트지 500매 15,000. 출력만 0, 베이직 8,000, 스탠다드 20,000, 프리미엄 30,000 |
| 배너 | 출력 수량 × 기본가 + 실내 거치대 + 실외 거치대 | 22,000 / 15,000 / 28,000 |

이 공식과 `tests/quote-baseline.test.ts`의 기대값이 판매 정책의 기준선이다. v2 시뮬레이터는 이 함수를 호출해 비교만 한다.

### 1.2 원가 데이터

실제 매입단가로 확인된 값은 없다.

코드 참고값은 다음뿐이다.

- DTF `dtfCostPerM` 1,350원/m. 화면의 참고 원가이며 공급가에 더하지 않는다. 100×100mm 10장은 참고 원가 280원, 판매 공급가 2,880원.
- DTF `dtfMinutesPerM` 5분/m. 예상 시간 표시용이다. 시급을 곱하지 않는다.
- 스티커 `stickerCutSecondsPerSheet` 30초/장. 예상 분 표시용이다. 금액에 들어가지 않는다.

시트 작업비 15,000원과 솔벤트 작업비 15,000원은 판매 공급가에 더하는 정액이다. 인건비 원장으로 쓰지 않는다.

### 1.3 제작 시간

금액과 연결된 공임 시간은 없다. 표시용 시간은 DTF 분/m와 스티커 장당 컷팅 초뿐이다. 열프레스, UV 출력, 재단, 조립, 포장 시간은 코드에 없다.

### 1.4 여러 품목이 나눌 수 있는 데이터

지금 파일은 품목마다 배치와 금액을 같이 계산한다. 아래만 나중에 공정 라이브러리로 올릴 수 있다.

- 롤 배치: POP 길이, 솔벤트 방향 선택, DTF 가로·세로 배치. 규칙은 서로 다르다. POP은 폭 안 변의 길이를 수량만큼 더하고, 솔벤트와 DTF는 폭 방향 개수와 진행 길이로 네스팅한다.
- 시트 배치: 스티커 A4·A3, 재단 여백 5mm, 간격.
- 10원 반올림과 부가세.
- 견적 성공·실패(`ok`, `error`). 0원을 정상 견적으로 보이지 않는 화면 규칙.
- 서버 설정 확인 후에만 금액을 보여주는 흐름, 공개 설정에서 인증값을 빼는 `toPublicConfig`.

자재 마스터, 장비 속도, 시급, 후가공, 로스, 포장비는 공유 테이블이 없다.

### 1.5 최소금액과 할인

- 스티커 시트만 최소 공급가 20,000원이 있다.
- 티셔츠만 수량 할인율이 있고, 주문 전체에 한 번 곱한다. 9장과 10장 공급가가 같고, 50장이 49장보다 싸다. 이 정책은 유지한다.
- UV는 수량 구간이 바뀌면 주문 전체 단가와 조정률이 바뀌어 총액이 내려가는 구간이 있다. 이 정책도 유지한다. 비교안은 `docs/price-inversion-options.md`.
- 급행비 필드는 없다. 명함 아트지 메모의 “2~3일”은 납기 문구이고 금액이 아니다.

### 1.6 관리자 화면에서 고칠 수 없는 설정

관리자 페이지는 공통(인증, 부가세, 기본 간격, 시트 작업비, 스티커 최소금액), POP, 스티커 재질 단가, 솔벤트, DTF, 명함, 배너만 편집한다.

데이터에는 있으나 화면 입력이 없는 것: 티셔츠 타입 단가, 2XL 추가금, 할인 구간, 시트 실크기, 재단 여백, 컷팅 초.

코드 상수라 저장 설정에도 없는 것: UV 면적 단가, 수량 구간, 조정률, UV 부가세 처리. 시트 크기와 재단 여백·컷팅 초는 `settings`와 `rates`에 있으나 관리자 입력 칸이 없다.

## 2. 새로운 원가 데이터 구조

원가 라이브러리는 판매 설정 `quotation_admin_config`와 다른 KV 키 `quotation_cost_library`에 둔다. 판매 설정 저장이 원가를 덮어쓰지 않고, 원가 저장이 판매가를 바꾸지 않는다. 이 키는 이번 설계 단계에서 만들지 않는다.

금액은 아래 공통 입력으로 저장한다. `unconfirmed`는 `amount`를 비운다. 0은 “비용 없음”으로 확인된 값만 쓰고, 미등록과 구분한다.

```ts
interface CostAmount {
  amount?: number;
  unit: "krw-per-m" | "krw-per-sheet" | "krw-per-ea" | "krw-per-min" | "krw-per-order";
  /** exclusive: 부가세 별도 공급가. inclusive: 부가세 포함 매입가. */
  tax: "exclusive" | "inclusive";
  status: "confirmed" | "code-reference" | "unconfirmed";
  /** 이 단가가 적용되기 시작하는 날짜. 시뮬레이션은 견적 기준일에 유효한 행을 고른다. */
  effectiveFrom: string;
  note?: string;
}

interface CostChange {
  revision: number;
  at: string;
  field: string;
  before?: number | string;
  after?: number | string;
}
```

부가세 포함 금액은 계산 전에 공급원가로 나눈다. 현재 부가세율 0.1이면 `공급원가 = 포함금액 / 1.1`이다. 포함 금액과 별도 금액을 한 합계에 그대로 더하지 않는다. 정규화에 쓴 부가세율도 이력에 남긴다.

수정할 때마다 `CostChange`를 라이브러리 개정 번호와 함께 쌓는다. 과거 견적은 최신 단가가 아니라 당시 `costLibraryRevision`이 가리키는 금액을 다시 보여줄 수 있어야 한다.

### 2.1 원자재·제품 매입단가

```ts
interface MaterialCost {
  id: string;
  label: string;
  kind: string;
  spec: string;
  active: boolean;
  purchaseUnit: "roll" | "box" | "m" | "m2" | "sheet" | "ea";
  usageUnit: "m" | "m2" | "sheet" | "ea";
  /** 구매단위 1개에 들어 있는 사용단위 수량. 롤 50m면 50. 단위가 같으면 1. */
  conversion?: number;
  conversionStatus: "confirmed" | "unconfirmed";
  price: CostAmount;
  /** 0.05는 5%. 필요량 / (1 - 로스율)만큼 소모한다. */
  wasteRate?: number;
  wasteStatus: "confirmed" | "unconfirmed";
  history: CostChange[];
}
```

관리자 화면에서 행을 추가·수정·비활성화한다. id는 서버가 만들고 이름과 분리한다. 품목이나 과거 견적이 참조하는 행은 삭제하지 않고 `active: false`로 둔다. 비활성 자재는 새 품목 선택 목록에서 빠지고, 이미 연결된 품목의 원가 분석과 과거 스냅샷에는 남는다.

구매단위와 사용단위가 같으면 환산은 1이다. 다르면 `사용단위 단가 = 매입가 / conversion`이다. `conversion`이 없거나 `conversionStatus`가 미등록이면 그 줄은 계산하지 않는다. 1:1로 가정하지 않는다.

로스율이 확인된 0이면 필요량만 쓴다. 미등록이면 0%로 두지 않고 그 줄을 누락으로 표시한다. 확인된 로스율의 소모량은 `필요 사용량 / (1 - 로스율)`이다.

예: DTF 필름, 솔벤트 원단, POP 원단, 아트지 시트, 티셔츠 공란, 맨투맨 공란, 에코백 본체, 피켓 막대, 아크릴 판. 초기 행은 단가와 환산, 로스가 비어 있다. DTF 1,350원/m는 자재 매입이 아니라 2.2의 코드 참고값으로만 연결한다.

### 2.2 장비별 출력 원가

```ts
interface EquipmentCost {
  id: string;
  label: string;
  price: CostAmount;
  rollWidthMm?: number;
  speed?: { value?: number; unit: "m-per-min" | "sheet-per-min" | "ea-per-min"; status: CostAmount["status"] };
  history: CostChange[];
}
```

DTF 장비 행만 `amount: 1350`, `unit: "krw-per-m"`, `tax: "exclusive"`, `status: "code-reference"`로 시드할 수 있다. 이 값을 판매단가나 확정 매입원가로 승격하지 않는다. 참고값만으로 만든 추천가격은 승인 버튼이 비활성이다.

### 2.3 작업 인건비와 소요시간

```ts
interface LaborRate {
  id: string;
  label: string;
  wage: CostAmount;
  history: CostChange[];
}
```

시급은 미확인이다. DTF 5분/m와 스티커 30초/장은 공정 시간의 코드 참고값이지 임금이 아니다. 시간은 금액 `CostAmount`와 별도 필드로 두고 단위는 `min-per-m`, `sec-per-sheet`, `min-per-ea` 중 하나로 적는다.

### 2.4 후가공 단가

코팅, 라미네이팅, 타공, 끈 조립, 어깨띠 봉제는 공정 원가 한 줄이다. `CostAmount`의 단위는 원/장, 원/개, 원/m 중 하나다. 초기값은 모두 미등록이다.

### 2.5 작업 세팅비

주문당 1회 원가다. `unit`은 `krw-per-order`다. 시트 작업비 15,000원과 솔벤트 작업비 15,000원은 판매가에 이미 포함된 정액이므로 원가 세팅비로 복사하지 않는다. 원가 세팅비 칸은 비워 둔다. 판매 정책의 세팅비는 4절의 판매 규칙에 그대로 남긴다.

### 2.6 불량·재료 로스율

```ts
interface WasteRate {
  id: string;
  label: string;
  rate?: number;
  status: "confirmed" | "code-reference" | "unconfirmed";
}
```

0.05는 5%다. 미확인 로스를 0%로 두고 원가를 계산하지 않는다.

### 2.7 포장과 기타 변동비

봉투, 택배 박스, 행택은 `CostAmount`로 저장한다. 단위는 원/개 또는 원/주문이다. 초기값은 미등록이다.

### 2.8 제품별 이익률 세 단계

이익률은 판매 공급가에서 이익이 차지하는 비율이다. 원가에 더하는 가산율이 아니다. 판매가를 원가로 나눠 역산한 값은 저장하지 않는다.

```ts
interface MarginPolicy {
  productId: string;
  /** 0.15는 판매가의 15%. 비어 있으면 해당 가격을 계산하지 않는다. */
  minimumRate?: number;
  targetRate?: number;
  highRate?: number;
  effectiveFrom: string;
  revision: number;
  history: CostChange[];
}
```

세 비율은 0 이상 1 미만이다. 하나라도 비어 있으면 그 칸의 추천가격만 비우고, 입력된 다른 칸은 계산한다. 공급원가 자체가 미등록이면 세 칸 모두 비운다.

### 2.9 최소 판매금액

원가 라이브러리에 두지 않는다. 판매 정책의 최소 공급가다. 스티커 20,000원만 현재 값이 있다.

## 3. 공통 제작 공정 구조

공정 id는 코드에 고정하지 않는다. 관리자가 새 공정을 등록하고, 품목은 그 id를 여러 줄에 연결한다. 사용 중인 공정은 삭제하지 않고 비활성화한다.

```ts
type ChargeMethod =
  | "per-ea"
  | "per-sheet"
  | "per-m"
  | "per-m2"
  | "per-minute"
  | "per-order"
  | "setup-plus-qty";

interface ProcessDef {
  id: string;
  label: string;
  active: boolean;
  method: ChargeMethod;
  /** 개당·장당·m당·㎡당 변동비, 또는 시간당이 아닌 방식의 단가. */
  variable?: CostAmount;
  /** per-minute일 때 분당 인건비. */
  laborPerMin?: CostAmount;
  /** per-minute일 때 분당 장비 운영비. */
  equipmentPerMin?: CostAmount;
  /** 작업시간. 단위는 분/개, 분/m, 분/주문. */
  minutes?: { value?: number; per: "ea" | "m" | "order"; status: CostAmount["status"] };
  /** 주문당 세팅비. per-order와 setup-plus-qty에서 사용. */
  setup?: CostAmount;
  history: CostChange[];
}

interface RecipeLine {
  lineId: string;
  refId: string;
  kind: "material" | "process";
  /** 같은 공정 id를 여러 lineId로 둘 수 있다. */
  usage: "per-order" | "per-piece" | "per-meter-layout" | "per-sheet-imposition" | "per-m2";
}

interface ProductRecipe {
  productId: string;
  label: string;
  active: boolean;
  /** 기존 8개만 채운다. 고객 견적은 승인 전 이 함수를 유지한다. */
  legacyQuoteId?: "pop" | "sticker-sheet" | "sticker-solvent" | "uv-acrylic-keyring" | "dtf" | "tshirt" | "business-card" | "banner";
  lines: RecipeLine[];
}
```

방식별 공급원가(부가세 정규화 후)는 다음과 같다. 선택한 방식에 필요한 금액이나 시간이 미등록이면 그 줄은 누락이다.

| 방식 | 계산 |
| --- | --- |
| 개당, 장당 | 단가 × 수량 |
| m당 | 단가 × 배치 길이(m) |
| ㎡당 | 단가 × 가로(m) × 세로(m) × 수량 |
| 작업시간당 | (분당 인건비 + 분당 장비 운영비) × 작업분 + 등록된 세팅비 |
| 주문당 고정 | 세팅비 1회 |
| 고정비 + 수량 비례 | 세팅비 + 개당 단가 × 수량 |

배치 길이와 시트 매수는 기존 POP·솔벤트·DTF·시트 함수의 길이·매수만 읽는다. 그 함수의 판매가는 원가에 넣지 않는다. 새 품목은 입력한 가로·세로·수량으로 길이와 면적을 계산한다.

에코백 예:

1. 자재 `eco-bag-blank`, 개당 1개
2. 공정 `dtf-print`, 디자인 크기 배치 길이
3. 공정 `heat-press`, 개당 1회
4. 공정 `pack`, 개당 1개

같은 `dtf-print`를 DTF 시트 판매, 티셔츠 전사, 에코백, 피켓, 어깨띠가 공유한다. 어깨띠는 자재 원단 + `solvent-print` 또는 `dtf-print` + `cut` + `pack`처럼 공정 조합만 바꾼다.

공정과 현재 품목의 대응은 다음과 같다. 비어 있는 칸은 코드에 단계가 없다는 뜻이다.

| 공정 | 현재 연결 | 시간·장비 상태 |
| --- | --- | --- |
| DTF 출력 | DTF 롤 배치 | 분/m와 1,350원/m는 코드 참고값 |
| 열프레스 | 없음 | 미확인 |
| 솔벤트 출력 | 솔벤트 롤 배치 | 롤 폭은 코드 참고값. 출력 원가 미확인 |
| UV 출력 | UV키링 가격식만 있음 | 장비 원가·시간 미확인 |
| 시트 출력 | 스티커 시트 배치 | 장당 판매단가만 있음 |
| 커팅 | 스티커 초/장 표시 | 코드 참고값. 공임 미확인 |
| 코팅·라미네이팅 | 없음. 투명데드롱은 재질 판매 옵션 | 미확인 |
| 재단 | 시트 여백 5mm | 치수는 코드 참고값. 공임 미확인 |
| 디자인 | 명함 등급 판매가 | 판매 요금. 공임 원가 미확인 |
| 조립 | 배너 거치대는 판매 단가 가산 | 조립 시간 미확인 |
| 포장 | 없음 | 미확인 |

새 품목은 레시피만 추가한다.

- 맨투맨: 공란 매입 + 인쇄 공정(DTF 또는 별도 나염) + 포장. 현재 후드·긴팔 판매단가와 할인표는 그대로 두고, 맨투맨은 새 상품 id로 둔다.
- 피켓: 판 또는 막대 매입 + 시트 또는 솔벤트 출력 + 재단 + 조립 + 포장.
- UV스티커: UV 출력 + 커팅. UV키링 가격식과 분리한다.
- 아크릴 굿즈: 아크릴 매입 + UV 또는 시트 + 커팅 + 조립. UV키링 레거시 공식과 별도 id다.

레시피가 있다고 견적 화면에 바로 나오지 않는다. 판매 정책이 연결되고, 그 정책이 레거시 기준선과 같거나 사용자가 새 가격을 승인하기 전에는 기존 품목 목록을 유지한다.

## 4. 품목별 가격 산정 방식

판매 정책은 원가 라이브러리 밖에 둔다. 품목마다 방식 하나를 고른다.

### A. 규격·수량별 고정 판매가

표 또는 단순 단가식이다. 현재 8개 품목의 실제 견적은 모두 이 층에 남긴다.

- 명함, 배너, 티셔츠 타입 단가, POP·솔벤트·DTF 미터 단가, 스티커 장당 단가, UV 구간식.
- UV와 티셔츠는 이 방식의 기존 구현을 유지한다. v2가 만든 가격은 시뮬레이션 화면에만 표시한다.

### B. 제작원가와 목표 이익률

이익률은 판매가 대비 이익이다. 원가에 비율을 더하는 가산율과 다른 공식이다.

```text
공급원가 = 부가세를 뺀 자재·공정 원가의 합
목표 판매 공급가 = 공급원가 / (1 - 목표이익률)
예상 이익금 = 목표 판매 공급가 - 공급원가
검산 이익률 = 예상 이익금 / 목표 판매 공급가
```

가산율 공식 `공급원가 × (1 + 가산율)`은 쓰지 않는다. 공급원가 10,000원일 때 둘은 이렇게 갈린다.

| 입력 25% | 판매 공급가 | 이익금 | 판매가 대비 이익률 |
| --- | ---: | ---: | ---: |
| 가산율 25% | 12,500 | 2,500 | 20% |
| 목표 이익률 25% | 13,333 후 10원 반올림 13,330 | 3,330 | 약 25% |

목표 이익률이 0 이상 1 미만일 때만 나눈다. 1 이상이면 계산하지 않고 “이익률은 100% 미만이어야 한다”를 반환한다.

같은 공급원가로 세 가격을 만든다. 각각 관리자가 품목에 저장한 이익률을 쓴다.

| 이름 | 공식 |
| --- | --- |
| 최소 수익성 가격 | `공급원가 / (1 - 최소이익률)` |
| 목표 판매가격 | `공급원가 / (1 - 목표이익률)` |
| 높은 수익성 가격 | `공급원가 / (1 - 고이익률)` |

셋 모두 10원 단위로 반올림한 공급가다. 부가세와 총액은 그 공급가에 기존 `calcVatAndTotal`을 적용해 옆에 보여 준다. 고객 견적의 대표 금액은 공급가이므로 차이 비교도 공급가 기준이다. UV 기존 화면만 최종가를 쓰므로, UV 비교 칸은 기존 최종가와 추천 공급가의 총액을 함께 적는다.

연결된 자재·공정 중 `unconfirmed`가 하나라도 있으면 세 가격을 만들지 않는다. 누락 id와 이름을 반환한다. 없는 금액을 0이나 판매단가로 채우지 않는다. `code-reference`만 있는 계산은 “참고 시뮬레이션”으로 표시하고 승인할 수 없다.

기존 웹 견적 공급가와의 차이는 `추천 목표 공급가 - 현재 판매 공급가`이다. 현재 판매 공급가는 기존 8개 계산 함수의 결과만 사용한다. 레거시 함수가 없는 새 품목은 현재 판매가를 비우고, 승인된 고정가 또는 승인된 추천가가 생기기 전에는 고객 화면에 올리지 않는다.

공헌이익은 판매 공급가에서 변동 공급원가를 뺀 금액이다. 주문당 세팅비는 고정비로 두고 공헌이익에서 빼지 않는다. 이익률은 `공헌이익 / 판매 공급가`이다. 비교 대상이 현재 웹 견적이면 그 공급가로 공헌이익을 계산한다. 현재 판매 공급가가 목표 판매가격보다 낮으면 “목표 이익률 미달” 경고를 낸다. 경고만 하고 판매가는 바꾸지 않는다.

최소 판매가격은 `공급원가 / (1 - 최소이익률)`과 품목에 등록된 최소 공급가 중 큰 값이다. 스티커의 기존 최소 공급가 20,000원은 판매 정책에 남긴다. 최소 이익률이 비어 있으면 등록된 최소 공급가만 적용하고, 둘 다 없으면 최소 판매가격 칸을 비운다.

### C. 매입과 복수 공정 합산

에코백처럼 자재 매입 + 공정 원가를 더해 공급원가를 만든 뒤 B의 세 가격을 계산한다. 공정 원가가 비어 있으면 합산을 멈추고 어느 공정이 비었는지 반환한다. 0원 합계를 성공 견적으로 내지 않는다.

### 공통 판매 규칙

방식 A·B·C 다음에 같은 순서로 적용한다.

1. 수량 할인. 할인 적용 범위는 `whole-order` 또는 `marginal`을 명시한다. 현재 티셔츠는 `whole-order`로 기록만 하고 계산은 기존 함수가 한다.
2. 최소 판매금액. 현재는 스티커 시트.
3. 급행 제작비. 칸만 두고 기본은 없음. 없음은 0원이고 미확인이 아니다.
4. 10원 반올림과 부가세. 기존 `calcVatAndTotal`. UV 레거시만 예외로 남긴다.
5. 수량 증가 시 총액 감소 경고. 시뮬레이터가 수량 1부터 스캔해 경고 목록을 만든다. 경고가 있어도 기존 UV·티셔츠 판매가는 바꾸지 않는다.

## 5. 관리자 화면과 API

현재 `/admin`은 판매 설정 편집기다. 인증 쿠키는 재사용하고, 원가 화면은 판매 탭과 분리한다. 고객 `/quote`와 공개 `GET /api/config`는 지금 응답 그대로 둔다.

구현 전 검토용 메뉴는 아래 일곱 개다. 판매가격 메뉴는 지금 화면을 유지한다. 나머지는 관리자 세션으로만 열린다.

| 메뉴 | 하는 일 |
| --- | --- |
| 판매가격 | 기존 8개 품목 판매 설정. 자동으로 바뀌지 않는다. |
| 원자재 | 추가, 수정, 비활성화. 이름, 종류, 규격, 구매단위, 사용단위, 환산, 매입가, 로스율, 적용일. |
| 제작 공정 | 새 공정 등록과 비활성화. 5.1의 비용 방식, 작업시간, 세팅비, 인건비, 장비 운영비. |
| 판매 품목 | 새 품목 생성, 원자재·공정 여러 줄 연결, 같은 공정 반복. 기존 8개는 레거시 견적 id를 유지한 채 분석용으로만 연결. |
| 수익성 | 총원가, 최소 판매가, 목표 추천가, 기존 판매가와 차액, 공헌이익, 이익률, 미등록·미달 경고. |
| 견적 이력 | 당시 원가 스냅샷과 당시 판매가. 최신 원가로 과거 금액을 다시 쓰지 않는다. |
| 배포 점검 | 테스트, 백업, 원복 절차 표시. 운영 배포 버튼은 두지 않는다. |

### 5.1 원가 등록

표 한 줄이 원자재 또는 공정 원가 하나다.

| 열 | 입력 |
| --- | --- |
| 구분 | 원자재, 장비 출력, 인건비, 후가공, 세팅, 로스, 포장 |
| 이름 | 표시 이름 |
| 금액 | 비어 있으면 미등록. 빈 칸을 0으로 저장하지 않는다. |
| 단위 | 원/m, 원/장, 원/개, 원/분, 원/주문 |
| 부가세 | 별도 또는 포함 |
| 적용일 | `effectiveFrom` |
| 상태 | 확인됨, 코드 참고값, 미등록 |
| 이력 | 해당 행의 개정 목록 |

저장은 `PUT /api/admin/cost-library`만 호출한다. 판매 설정 revision은 올라가지 않는다.

### 5.2 품목 연결

품목을 고르면 체크한 원자재와 공정만 그 품목 레시피에 들어간다. 각 줄에 소요 방식을 고른다. `주문당`, `개당`, `배치 길이 m`, `시트 매수`. 수량·사이즈·옵션은 시뮬레이션 탭의 입력이다. 연결 자체는 판매단가를 바꾸지 않는다.

에코백은 본체 1개, DTF 배치 길이, 열프레스 1회, 포장 1개로 연결한다. 기존 POP·스티커·솔벤트·DTF·명함·배너·티셔츠·UV도 같은 화면에서 연결할 수 있으나, 연결 전에는 추천가격 탭이 “레시피 없음”만 보여 준다.

### 5.3 수익성 시뮬레이션

입력은 고객 견적과 같은 수량, 사이즈, 옵션이다. 서버가 레거시 판매가를 읽기 전용으로 계산하고, 원가 라이브러리로 추천가만 따로 계산한다.

화면 블록:

1. 총제작원가. 줄마다 이름, 수량, 단위, 부가세 처리 전 금액, 공급원가.
2. 미등록 목록. 가격 칸은 비운다.
3. 원가가 모두 확인된 경우에만 최소 수익성 가격, 목표 판매가격, 높은 수익성 가격. 각 칸에 공급가, 이익금, 이익률, 부가세 포함 총액.
4. 현재 웹 견적 공급가, 추천 목표 공급가, 차액, 차이 비율.
5. 이번 계산에 쓴 `costLibraryRevision`, 판매 `configMeta.revision`, 이익률 적용일.

승인 버튼은 이 결과 아래에 따로 둔다. 버튼을 누르기 전에는 어떤 저장도 판매 설정을 수정하지 않는다. 누를 때는 품목, 추천 가격, 적용 범위를 다시 보여 주고 확인 후에만 판매 정책 개정을 만든다. 참고값이나 미등록이 있으면 버튼이 눌리지 않는다. 이번 설계 단계에서는 버튼 동작도 구현하지 않는다.

### 5.4 API 경계

| API | 인증 | 하는 일 | 하지 않는 일 |
| --- | --- | --- | --- |
| `GET /api/config` | 없음 | 공개 판매 설정 | 원가, 이익률, 이익금, 개정 이력 |
| `GET·PUT /api/admin/cost-library` | 관리자 세션 | 원가 조회·수정 | 판매 KV 기록 |
| `POST /api/admin/pricing-simulation` | 관리자 세션 | 원가합, 세 가격, 기존 판매가와 차이, 누락 목록 | 판매가 저장, 브라우저 공개 캐시 기록 |
| `POST /api/admin/pricing-approval` | 관리자 세션과 확인 본문 | 승인된 추천가만 판매 정책에 반영 | 자동 반영, 미등록 원가로 반영 |

시뮬레이션 응답은 관리자 화면에만 둔다. `rememberServerConfig`와 공개 견적 캐시에 넣지 않는다.

### 5.5 견적 이력에 남길 버전

이력 키는 `quotation_quote_log`로 판매 설정 JSON과 분리한다. 한 건은 다음을 보관한다.

```ts
interface QuoteHistoryEntry {
  id: string;
  createdAt: string;
  productId: string;
  input: Record<string, number | string>;
  salePolicyRevision: number;
  costLibraryRevision: number;
  marginPolicyRevision: number;
  /** 고객에게 제시한 공급가. 승인 전에는 기존 판매가와 같다. */
  presentedSupplyPrice: number;
  presentedVat: number;
  presentedTotal: number;
  /** 관리자 조회용. 공개 견적 응답에 포함하지 않는다. */
  internal?: {
    supplyCost?: number;
    minimumSupplyPrice?: number;
    targetSupplyPrice?: number;
    highSupplyPrice?: number;
    profit?: number;
    marginRate?: number;
    missing: string[];
  };
}
```

고객용 이력 조회는 `internal`을 제거한다. 원가를 나중에 고쳐도 과거 건은 저장된 revision의 스냅샷으로 설명한다. 스냅샷이 크면 revision 번호와 함께 당시 원가 행의 사본을 이력 문서 안에 둔다.

## 6. 기존 설정값과의 호환

- `AppConfig` 필드는 유지한다. `normalizeConfig`는 없는 품목과 솔벤트 단가 마이그레이션만 하고, 원가 필드를 만들어 채우지 않는다.
- 구버전 KV에 `engine` 블록이 없어도 견적은 지금 함수로 계산된다.
- 원가 라이브러리가 없거나 읽기 실패여도 판매 견적은 동작한다. 시뮬레이션만 “원가 자료를 읽지 못했다”고 표시한다.
- 판매 설정의 `solventSellPerM`, POP 단가, 티셔츠 단가, 명함 표, UV 상수는 원가 시드의 입력이 아니다.
- 코드 참고값 시드는 별도 초기 파일에서 id로만 연결한다. 예: 장비 `dtf`의 `variableCost`가 `settings.dtfCostPerM`과 같은 1,350인지 테스트로 확인한다. 사용자가 참고값을 고쳐도 판매 `dtfSellPerM`은 그대로다.
- 설정 버전 `configMeta.revision`은 판매 저장에만 올린다.

## 7. 원가 데이터가 없을 때

- 방식 A 기존 품목: 원가와 무관하게 지금 판매가를 표시한다.
- 방식 B·C 시뮬레이션: 비어 있는 자재·장비·임금·로스 이름 목록을 반환하고 추천 공급가는 비운다. 0원을 추천가격으로 두지 않는다.
- 코드 참고값만 있는 줄은 누락 목록과 별도로 “참고값” 목록에 넣고, 그 상태로는 승인하지 못한다.
- 새 품목(에코백, 피켓, 어깨띠, UV스티커, 아크릴 굿즈, 맨투맨): 고정 판매표를 사용자가 넣기 전에는 견적 폼에 올리지 않는다. 고정표가 있으면 방식 A로 팔 수 있고, 원가는 나중에 붙여 수익성만 본다.
- 로스율 미확인을 0으로 대체하지 않는다. 포장비 미확인을 0으로 대체하지 않는다. 급행을 선택하지 않은 경우는 0원이다.

## 8. 사용자에게 확인할 매입단가·공임

아래는 칸의 목록이다. 현재 판매가를 제안 원가로 적지 않았다.

자재 매입, 단위와 함께:

- DTF 필름 또는 잉크 포함 미터 원가. 코드의 1,350원/m가 매입 원가인지, 잉크·전기·감가까지인지.
- 솔벤트 원단 미터 매입가, 롤 폭 620mm가 실제 폭인지.
- POP 원단 미터 매입가, 롤 폭 610mm가 실제 폭인지. 4-cut과 2-cut의 원단 소모 차이.
- 아트지, 모조지, 유포지, 투명데드롱 시트 매입가. A4·A3 별도인지.
- 명함 용지 매입가. 수입 당일제와 아트지가 외주 매입인지 자체 인쇄인지.
- 배너 원단 장당 매입가, 실내·실외 거치대 매입가.
- 티셔츠·맨투맨·후드 공란 사이즈별 매입가. 2XL 추가가 매입 차이인지 판매 할증인지.
- 에코백 본체, 피켓 판·막대, 어깨띠 원단, 아크릴 판, UV스티커 미디어 매입가.

인력·장비:

- 분당 또는 시간당 인건비.
- DTF 5분/m, 스티커 컷팅 30초/장이 실제 작업 시간인지.
- 열프레스 1회 시간과 전기·소모품.
- UV 출력 면적당 원가와 시간.
- 코팅·라미네이팅, 재단, 조립, 포장의 1회 시간 또는 건당 비용.
- 주문당 실제 세팅에 드는 시간. 판매 작업비 15,000원과 별개로.
- 품목별 불량·로스율.
- 품목별 목표 이익률, 최소 판매금액, 급행 요금.

공정 확인:

- POP을 롤에 여러 장 네스팅하는지, 지금처럼 한 장 길이를 수량만큼 더하는지.
- 에코백·피켓·어깨띠에 DTF와 열프레스가 들어가는지, 솔벤트만 쓰는지.

## 9. 단계별 구현 순서

각 단계는 설계 확인 후, 앞 단계의 판매가 기준선 테스트가 통과한 뒤에 시작한다. 이번 문서 작성은 0단계이며 코드를 포함하지 않는다.

1. 원자재·공정·품목 레시피 타입과 빈 라이브러리. 공개 설정 응답에 원가를 넣지 않는다. 기존 계산 파일은 수정하지 않는다.
2. 관리자 화면에서 원자재와 공정을 추가·수정·비활성화. 단위 환산, 로스, 적용일, 이력을 저장한다.
3. 판매 품목 생성과 줄 단위 연결. 기존 8개에는 `legacyQuoteId`만 붙이고 고객 견적 분기는 레거시 함수를 유지한다.
4. 관리자 전용 시뮬레이터. 공급원가, 최소 판매가, 목표 추천가, 공헌이익, 이익률, 기존 판매가와의 차액, 미등록·미달 경고.
5. 수익성 화면. 승인 API는 확인 본문이 있을 때만 판매 개정을 만들게 설계하고, 그 전엔 판매 KV를 쓰지 않는다.
6. 견적 이력에 원가 줄 스냅샷과 당시 판매가를 저장하는 관리자 API.
7. 명함 미등록 디자인 등급 수정. 11절의 작은 수정안이며, 판매 표와 등록 등급 금액은 유지한다.
8. 마이그레이션 리허설, 자동 테스트, 미리보기 배포. 운영 KV의 판매 설정은 복사하거나 덮어쓰지 않는다.
9. 설계와 미리보기 확인이 끝난 뒤에만 운영 배포. 절차는 14절이다.
10. 기존 8개 품목의 화면 판매가를 방식 B·C로 바꾸는 작업과 UV·티셔츠 가격 역전 수정은 그 다음의 별도 승인이다. 비교안은 `docs/price-inversion-options.md`다.

## 10. 기존 견적가격을 보호하는 테스트

유지할 테스트:

- `tests/quote-baseline.test.ts`의 8개 품목 정상 입력. POP 200×200mm 10장 공급가 126,900 / 총액 139,590, 솔벤트 50×50mm 100장 49,900 / 54,890, DTF 100×100mm 10장 2,880 / 3,170, 명함 수입 100매 베이직 28,000 / 30,800을 포함한다.
- `tests/calc-errors.test.ts`의 배치 불가·미등록 매수.
- `tests/known-defects.test.ts`의 UV·티셔츠 역전. 정책을 바꾸기 전까지 기대값을 유지한다.
- `tests/config-resolution.test.ts`의 서버 설정 우선순위와 인증값 제거.

추가할 테스트는 시뮬레이터와 저장 경계에만 둔다.

- 원가 라이브러리를 비우거나 판매단가와 같은 숫자를 넣어도 `calcPop`, `calcDtf`, `calcTshirt`, `calculateQuote` 결과가 변하지 않는다.
- 원가 저장 함수가 `quotation_admin_config`를 쓰지 않는다.
- 공개 설정 JSON에 `purchasePrice`, `wagePerMin`이 없다.
- DTF 참고 시드 1,350은 `code-reference`이고, 판매 13,900과 필드가 다르다.
- 방식 B는 자재 상태가 `unconfirmed`이면 추천 공급가를 만들지 않고 누락 이름을 반환한다.
- 공급원가 10,000원, 목표 이익률 25%의 추천 공급가는 13,330원이다. 가산율 25%의 12,500원과 다르다.
- 시뮬레이션 응답을 공개 설정 저장 함수에 넘겨도 판매 단가 필드는 그대로다.
- 승인 API는 확인 본문이 있을 때만 판매 개정을 만들도록 설계하고, 구현 전에는 호출하지 않는다.
- 수량 스캔 경고가 UV 45×30mm 1개 7,260원, 2개 4,562원을 감지하되 `calculateQuote` 반환값은 그대로다.

화면 판매가를 바꾸는 PR은 기준선 테스트의 기대값을 함께 바꾸는 경우에만 통과시킨다. 기대값 변경에는 승인한 품목과 수량 목록이 있어야 한다.

## 11. 명함 미등록 디자인 등급

현재 `calcBusinessCard`는 용지와 매수가 등록돼 있으면 등급 id가 목록에 없어도 `designFee`를 0으로 두고 `ok: true`를 반환한다. 등록된 “출력만” 등급도 요금이 0원이라, 오타 id와 의도된 출력만이 같은 금액이 된다.

견적 화면은 등급 선택을 등록된 id만 쓰므로 일반 조작에서는 재현되지 않는다. 함수를 직접 부르거나 저장된 id가 삭제된 경우에는 인쇄비 견적이 그대로 확정된다.

수정안은 계산식과 요금표를 그대로 둔다.

- 등급 id가 목록에 있으면 그 `fee`를 쓴다. 0원 등록 등급은 성공이다.
- 등급 id가 없으면 `ok: false`, 오류 “등록되지 않은 디자인 등급입니다.” 공급가·부가세·총액은 화면에 올리지 않는다. 2차에서 미등록 매수에 적용한 방식과 같다.
- 폼의 기본 선택은 지금처럼 목록의 첫 등급이다.
- 테스트: 없는 id는 실패. `output-only` 100매는 인쇄비 20,000원 성공. `basic` 100매는 공급가 28,000원, 총액 30,800원.

이 수정은 9절 7단계의 작은 패치로 미룬다. 이번 설계에는 포함하지 않는다.

## 12. 신규 품목 등록 흐름

1. 판매 품목 메뉴에서 이름만 저장한다. 서버가 품목 id를 만든다. 고객 견적 목록에는 보이지 않는다.
2. 활성 원자재를 한 줄씩 추가한다. 줄마다 소요 방식을 고른다. 같은 자재를 여러 줄에 둘 수 있다.
3. 활성 공정을 한 줄씩 추가한다. 같은 공정 id를 다른 `lineId`로 여러 번 넣을 수 있다. 예: 인쇄 후 재단, 다시 인쇄.
4. 수량, 가로, 세로 샘플로 수익성 계산을 연다. 미등록 환산, 로스, 단가, 작업시간이 있으면 이름만 경고하고 추천가를 비운다.
5. 원가가 모두 확인되면 최소 판매가, 목표 추천가, 공헌이익, 이익률이 나온다. 기존 8개에 연결한 경우에는 현재 웹 견적과 차액, 목표 이익률 미달 경고가 함께 나온다.
6. 고객에게 팔 가격을 정하는 방법은 둘이다. 관리자가 고정 판매가를 직접 입력하거나, 추천가를 확인하고 승인한다. 어느 쪽도 자동 저장되지 않는다.
7. “고객 견적에 표시”를 켜야 품목 목록에 나온다. 기존 8개는 이 스위치를 켜지 않아도 지금 견적 화면을 유지한다. 새 품목 표시는 판매가 승인이 있을 때만 허용한다.

에코백 예는 본체 1개, DTF 출력 1회, 열프레스 1회, 포장 1개다. 어깨띠는 원단, 출력, 커팅, 포장으로 줄을 바꾸면 된다. 맨투맨, 피켓, UV스티커, 아크릴 굿즈도 같은 흐름이다. 현재 티셔츠·UV키링 판매 공식은 각 품목의 `legacyQuoteId`에 남긴다.

## 13. 마이그레이션, 테스트, 원복

마이그레이션은 새 키만 만든다.

- `quotation_cost_library`: 원자재, 공정, 품목 레시피, 이익률, 개정 이력
- `quotation_quote_log`: 견적 시점의 원가 줄과 판매가 사본
- `quotation_admin_config`: 읽기만 한다. 필드 추가나 판매가 재기록은 승인 API 이전에는 없다.

구버전 판매 JSON에 원가 키가 없어도 `normalizeConfig`는 지금처럼 품목과 솔벤트 단가만 맞춘다. 원가 라이브러리가 없거나 읽히지 않아도 기존 8개 견적은 동작한다.

원가 변경은 오늘 기준 분석에 바로 반영한다. 적용일이 미래인 단가는 그 날짜 전에 쓰지 않는다. 과거 견적 문서는 저장 당시 줄 사본을 가지므로 이후 단가 수정, 비활성화, 환산 변경의 영향을 받지 않는다.

자동 테스트는 10절에 더해 다음을 둔다.

- 구매단위 롤, 사용단위 m, 환산 50, 매입 100,000원, 로스 5%, 필요 2.5m의 공급원가는 5,263원이다. 계산은 `2.5 / 0.95 × (100000 / 50)`.
- 환산 또는 로스가 미등록이면 추천가가 없고 해당 자재 이름이 누락 목록에 있다. 금액은 0이 아니다.
- 사용 중인 자재 삭제 요청은 실패하고 비활성화만 성공한다. 비활성 자재는 새 선택 목록에 없고 기존 레시피 분석에는 남는다.
- 같은 공정 id를 두 줄 넣으면 두 줄의 원가가 더해진다.
- 현재 판매가가 목표 추천가보다 낮으면 미달 경고가 있고 판매 설정 금액은 그대로다.
- 공개 `/api/config` 응답에 매입가, 로스, 이익률, 공헌이익 필드가 없다.

원복은 판매 설정을 되돌릴 필요가 없다. 원가 기능을 끄는 스위치 기본값은 꺼짐이다. 문제가 생기면 스위치를 끄고 직전 배포로 되돌린다. 새 KV 키는 남겨 두어도 고객 견적이 읽지 않는다. 판매 키를 백업에서 덮어쓰는 복구 스크립트는 실행하지 않는다.

## 14. 배포 게이트

운영 배포는 이 설계를 확인한 뒤의 단계다. 이번 작업에서는 배포하지 않는다.

확인 후 배포할 때의 순서는 다음과 같다.

1. `npm test`와 `npm run build`가 통과한다.
2. 기존 8개 정상 입력의 공급가와 총액이 기준선과 같다.
3. 미리보기 배포에서 관리자 로그인 후에만 원가 화면이 열린다. 공개 견적 화면의 8개 금액은 그대로다.
4. 운영 KV에 쓰기 전에 판매 설정을 읽기 전용으로 백업한다. 백업 파일에 인증값과 원가를 함께 넣지 않는다.
5. 운영에는 스위치가 꺼진 상태로 배포한다. 원자재 입력은 관리자가 미리보기에서 먼저 확인한다.
6. 되돌릴 때는 직전 배포로 재배포하고 스위치를 끈다. 운영 판매 KV는 복구 쓰기를 하지 않는다.

## 15. 한 줄 구조

```text
원가 라이브러리 (단위, 부가세 구분, 적용일, 개정 이력, 공개 안 함)
        ↓ 관리자 API만
품목 레시피 (원자재 + 공정, 수량·사이즈·옵션으로 공급원가)
        ↓
추천가격 3종 = 공급원가 / (1 - 이익률)
현재 웹 견적과 차액, 이익금, 이익률
        ↓ 승인 버튼을 누르기 전
지금 8개 품목 화면 견적 (기존 함수, 기존 KV)
        ↓ 승인 후 별도 판매 개정
견적 이력에 판매 개정 번호와 원가 개정 번호 보존
```
